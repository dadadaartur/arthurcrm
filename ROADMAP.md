## 0. Стек и масштаб — коротко

Next.js 14.2 (Pages Router, папки `app/` нет), React 18, Supabase
(Postgres + Auth + Storage), Tailwind, деплой на Vercel, оплата — ЮKassa.
~90 страниц, ~50 API-роутов, 64 таблицы в БД. Два раунда security-аудита уже
пройдены раньше (privilege escalation, race conditions, IDOR — см.
`CHANGELOG.md`), так что этот раунд — про продукт и дизайн, не про дыры в
безопасности (хотя парочка всё равно попалась, см. «Раунд 3»).

## 1. Важная находка: часть запрошенного уже наполовину заложена в БД

Схема Supabase заметно опережает интерфейс — 13 таблиц существуют в БД, но
не встречаются ни в одном файле кода (проверено grep по всему `pages/` и
`lib/`): `role_permissions`, `chat_sessions`, `chat_messages`,
`chat_templates`, `chat_ratings`, `goal_assignments`, `goal_indicators`,
`goal_tasks`, `services`, `approval_requests`, `employee_levels`,
`employee_mastery`, `mastery_levels`. Ещё несколько используются в одном-двух
местах по касательной: `departments` — только как выпадающий список в
`profile.js`, `deals` — просто строка в `<option>` на странице целей, ни разу
не запрос к таблице.

Это значит, что часть пунктов ТЗ — не «с нуля», а «доделать то, что заложено,
но не подключено»:

- **Для п.7 (CRM-имитатор):** таблицы `deals`, `chat_sessions`,
  `chat_messages`, `chat_templates`, `chat_ratings` — это готовая схема под
  внутреннюю мини-CRM (сделки + переписка + рейтинги), но ни одной страницы
  или API-роута для них нет. Плюс уже есть `lib/kpiSource.js` с функцией
  `pullAutoValues()` — коннектор «дай URL, получи `[{email, value}]`, запишу
  как значения KPI» — но эта функция нигде не вызывается (ни из cron, ни из
  API). Это значит автосбор показателей по `source: 'auto'` сейчас в принципе
  не работает, даже если админ его включит.
- **Для п.6 (архитектура компании):** таблицы `departments`, `roles`,
  `role_permissions`, `positions` есть, но реальная модель прав в
  `lib/permissions.js` — плоская: `is_company_admin` (булево) +
  4 отдельных флага (`can_create_tasks`, `can_review_tasks`,
  `can_manage_employees`, `can_delete_employees`) прямо в `profiles`, без
  понятия «отдел» или «руководитель — подчинённый». Иерархии в коде нет
  вообще.
- **Для п.8 (план развития):** `adaptation_templates` уже поддерживает
  шаблоны с днями/событиями (то, что вы просите сделать для плана
  адаптации), но параллельного механизма для «плана развития» опытных
  сотрудников нет — `employee_levels`/`employee_mastery`/`mastery_levels`
  не используются нигде, то есть это тоже задел, а не готовый функционал.

Дальше по каждому пункту — что именно нашёл и что предлагаю делать.

### п.5 — гибкие пороги целей
Текущая модель: у каждого показателя (`kpi_metrics`) ровно 4 фиксированных
столбца в БД — `thr_min`, `thr_mid`, `thr_top`, `thr_ultra` (плюс
`energy_*`/`karma_*` на каждый) — это и есть те самые «жёстко заданные 4
порога». Сделать по-настоящему гибким (переменное число порогов) — это
смена схемы: строки вместо столбцов, отдельная таблица вида
`kpi_metric_thresholds (metric_id, band_key, label, threshold_value,
color, sort_order)`. `lib/kpi.js` (`bandFor`, `energyFor`, `karmaFor`) сейчас
жёстко перебирает `thr_min/mid/top/ultra` по имени столбца — тоже придётся
переписать на цикл по строкам. Текущую 4-уровневую модель (мин/средний/топ/
ультра) оставляю как **шаблон по умолчанию** при создании показателя, как вы
и просили — просто он перестаёт быть единственным вариантом.

Карточки целей (`pages/goals.js`) разобрал построчно — обе жалобы
подтвердились в коде, не только на вид:
- название показателя обрезается через `text-overflow: ellipsis` с
  hover-тултипом (`title={m.name}`) — на тач-экранах (телефон) тултип
  недоступен вообще, то есть длинное название реально нечем посмотреть
  целиком;
- все 4 порога сейчас выводятся одной серой строкой в 10px: `мин {X} ·
  средн {Y} · топ {Z} · ультра {W}` — тоже с обрезкой по ellipsis при
  недостатке места, и без единого намёка на цвет, хотя `BAND_COLORS`
  (карта цвет-на-каждый-уровень) уже есть и используется рядом на этой же
  карточке для текущего уровня.

Правки: 4 отдельные цветные пилюли вместо одной обрезаемой строки (цвета
берём из уже существующего `BAND_COLORS`, это буквально готовая палитра —
не нужно ничего придумывать), плюс перенос полного названия в
детальную модалку по клику (клик по карточке уже открывает модалку —
`onClick={() => setDetailsMetric(m)}`, просто нужно проверить, что там
название не обрезано, и при необходимости — перенос на 2 строки на самой
карточке вместо однострочного ellipsis).

### п.4 — задания за цели с автозачётом
Задел уже есть и весьма приличный: у задания (`tasks`) уже есть
`is_auto_goal`, `auto_goal_condition` (варианты «все показатели ≥ мин»,
«все ≥ средний», «любой один ≥ мин»), `auto_energy`, и cron
(`check-deadlines.js`, секция 3) уже реально считает и зачисляет награду раз
в день, с защитой от повторного начисления (`task_auto_grants` с уникальным
индексом). Форма создания в `company-admin/tasks.js` уже даёт админу
включить этот режим при создании задания — то есть кнопка/модуль по факту
частично существует, просто скромно (чекбокс в общей форме, а не отдельная
кнопка/модуль, как вы просите).

Чего не хватает под ваш конкретный пример («задание выполнить цель звонки
на уровень ультра, награда такая-то»): в БД у `tasks` уже есть столбец
`auto_metric_id` (внешний ключ на `kpi_metrics`) — то есть предусмотрено
«привязать задание к ОДНОМУ конкретному показателю», но нигде в коде это
поле не используется — текущие 3 условия («все»/«любой») всегда смотрят на
**все** активные показатели компании сразу, выбрать один конкретный
(«именно звонки, именно на ультра») нельзя. План: подключить
`auto_metric_id` + новый режим условия «конкретный показатель ≥ конкретный
порог» в форме и в cron, вынести это в отдельную кнопку/страницу
(«Автозадания») в разделе управления заданиями, как вы просили в п.7.

## Фаза C — План адаптации и план развития

*п.8 — самый «сырой» участок по вашим же словам, и на деле тоже — самый
крупный пункт после архитектуры компании (Фаза H).*

Текущее состояние (смотрел `pages/onboarding.js` и `pages/company-admin/
adaptation.js` в коде, не только по названиям таблиц): система не с нуля —
`adaptation_plans` + `adaptation_plan_events` + `adaptation_templates` уже
рабочие. У каждого события уже есть день, **время** (`event_time` — то есть
почасовая привязка в схеме уже предусмотрена), тип, статус,
подтверждение сотрудника (`employee_confirmed_at` + `employee_feedback`) и
подтверждение руководителя (`manager_confirmed_at` + `rating`). То есть
скелет журнала взаимодействий, который вы просите, местами уже существует
— просто заточен только под адаптацию и очень скупо развит.

Конкретные находки:
- Никакого уведомления «событие наступает» нет — ни cron, ни триггера,
  привязанного к `event_time`. Сотрудник узнаёт о событии, только если сам
  зайдёт на страницу онбординга. Это и есть отсутствие «уведомлений о

# SQL-миграции

Эти файлы нужно применить в Supabase (SQL Editor → New query → вставить
содержимое файла → Run), **по одному, по порядку номеров**, до того как
соответствующий код из этого фикс-сета уйдёт в продакшен:

| Файл | Нужен для | Ломает что-то без него? |
|---|---|---|
| `001_transfer_karma.sql` | `pages/api/transfer.js` | Да — новый `pages/api/transfer.js` вызывает `rpc('transfer_karma', …)` и без миграции будет падать с ошибкой на каждом переводе |
| `002_rate_limiting.sql` | `lib/rateLimit.js` | Да — без таблицы `rate_limit_hits` лимитер будет падать на каждый запрос к защищённым эндпоинтам (перевод, создание платежа) |
| `003_profiles_privilege_columns.sql` | Защита от эскалации прав (находка аудита №3) | Нет — это дополнительный слой защиты, ничего не сломает при отсутствии, но и не защитит без применения |
| `004_minor_db_hygiene.sql` | Мелкие находки №17 (unique-индекс, дублирующийся индекс) | Нет — чисто гигиена, ничего не ломает и не чинит функционал |
| `005_flexible_kpi_thresholds.sql` | Гибкие пороги целей (п.5) и точный таргетинг авто-заданий (п.4) | Нет — оба новых столбца nullable, старые показатели и задания продолжают работать по старым столбцам без изменений |
| `006_adaptation_development_plans.sql` | План развития (п.8) — новый `kind` у планов/шаблонов, поле оценки фидбека, дедупликация уведомлений о событиях | Нет — все новые столбцы nullable/со значением по умолчанию, плюс 3 стартовых шаблона плана развития (безопасно вставляются повторно — не задвоятся) |

## Важно — я не подключён к вашей базе напрямую

Все три файла написаны по тому, что видно в коде приложения и по списку
индексов из выгруженных вами CSV — **не по прямому дампу схемы**. Это
значит:

- Имена таблиц/колонок должны быть верными (они видны прямо в коде,
  который эти таблицы читает и пишет), но **типы** (`numeric` vs `bigint`
  vs `integer` для `balance`/`amount`) — предположение по тому, как они
  используются в JS. Postgres обычно нормально работает с арифметикой
  между этими типами, но проверьте перед продакшеном.
- Прогоните на стейджинге/тестовом проекте Supabase (или хотя бы на копии
  продакшен-базы) **перед тем как применять на реальных данных с реальными
  деньгами**.
- После применения `001` и `003` можно быстро проверить, что вызов
  `rpc('transfer_karma', …)` вообще виден PostgREST — если сразу после
  применения появляется ошибка `Could not find the function in the schema
  cache`, подождите минуту (кэш обновляется periodically) или вызовите
  `notify pgrst, 'reload schema';` ещё раз вручную.

## Порядок отката

Если что-то пошло не так после применения:

- **001**: `drop function if exists public.transfer_karma(uuid, uuid, numeric, text);` — после этого старый (небезопасный) `pages/api/transfer.js` работать не будет, новый тоже, так что откатывайте вместе с кодом.
- **002**: `drop table if exists public.rate_limit_hits;` — безопасно, лимитер в коде написан так, что при ошибке БД он **не блокирует** запрос (fail open), см. `lib/rateLimit.js`.
- **003**: `drop trigger if exists protect_privileged_profile_columns on public.profiles; drop function if exists public.protect_privileged_profile_columns();`
